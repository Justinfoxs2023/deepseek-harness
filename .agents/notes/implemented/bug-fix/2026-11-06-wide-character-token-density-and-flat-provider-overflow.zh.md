# Agent Note: 宽字符 token 密度与平铺的提供方溢出响应体

Status: implemented

[English](2026-11-06-wide-character-token-density-and-flat-provider-overflow.md) | 中文

## 问题

提供方会拒绝超出其上下文窗口的请求，而 harness 必须识别这次拒绝、压缩对话并重试。这条路径上有三处缺口。

token meter 把每个字符都按四分之一个 token 计价。一份中文记录的计量结果只有提供方自身计数的一小部分，于是主动的压力压缩在提供方越过真实窗口很久之后才触发，对话持续增长，直到被提供方拒绝。

DeepSeek 适配器只从包裹的 `error` 对象读取提供方错误字段。以同样字段平铺作答的提供方或网关会丢掉提供方的 message 与 type，于是上下文超限的拒绝被读成普通的坏请求，恢复路径根本进不去。

第三处缺口掩盖了其余失败：恢复无法推进时，harness 保留了提供方错误，却没有说明原因。

## 决策

### 宽字符各计一个 token

`dsh-token-meter` 的固定密度把一个宽字符——CJK 表意文字、日文假名、谚文与全角形式——按一个 token 计价，其余字符每四个共享一个 token。在 MiniMax-M2.7 自己的 OpenAI 兼容端点上实测：2880 个字符的中文记录报告 1853 个提示词 token；原先的密度给出 754（提供方计数的 0.41），宽字符密度给出 2892（1.56）。代码与英文样本没有变化，因为它们不含宽字符。因此这条规则在 CJK 内容上偏高估，让压力阈值保持保守。

`ctx.tokenMeter` 保持与模型无关：一个 fold、一个估算器，没有配置也没有按模型的画像。镜像构成投影的仅客户端 fixture 镜像同样的密度，因此 fixture 的构成行与 meter 一致。

### 提供方错误字段既从包裹体也从平铺体读取

`dsh-llm-deepseek` 既从包裹的 `error` 对象读取提供方错误字段，也从携带同样字段的平铺响应体读取。平铺的上下文超限响应体现在被判定为 `CONTEXT_WINDOW_EXCEEDED` 而不是普通的坏请求，压缩恢复路径因此可达。两种形态都不吻合的响应体仍以 HTTP 状态码为权威。pi-ai 路由从提供方自己的 message 文本识别同一次拒绝——该文本本就已点明溢出。

### 无法推进的恢复会说明原因

`dsh-compaction-basic` 以警告级别记录上下文溢出恢复保留原始提供方错误的每一种原因：没有路由请求目标、尝试预算耗尽、以及压缩后表层没有变化。该轮次的失败仍然是提供方自己的错误，改变的只是可见性。

## 测试

估算器测试锁定宽字符每字符一个 token、其余字符每四字符一个 token、同一块内容中混合的两种密度、假名／谚文／全角形式，以及工具 schema 与系统消息的价格。适配器测试通过真实 HTTP 路径覆盖平铺的上下文超限响应体，同时断言规范代码与被保留的提供方 message。

## 考虑过的替代方案

- **所有字符共用一种密度**——不予采纳，因为 CJK 记录会被定价为提供方实际规模的四分之一，压力压缩在提供方已经拒绝请求之后才触发。按宽字符一个 token 计价则改为高估同一份记录，让阈值保持保守。
- **采用按提供方的精确分词器**——不予采纳，因为每个消费方的测量必须一致且回放稳定，而没有任何部署提供 meter 需要的分词器。
- **只从包裹对象读取提供方字段**——不予采纳，因为把信封拍平的网关会把上下文超限的拒绝变成无效请求，恢复路径根本进不去。
- **把失败的恢复报成错误**——不予采纳，因为该轮次的失败仍然是提供方自己的错误；日志行只做解释，不改变结果。

## 后果

压力阈值对 CJK 记录现在基本名副其实：对话在达到所配置窗口比例时就被压缩，而不是晚好几倍。估算器对 MiniMax 的 CJK 内容约高估一半，所以中文会话比提供方严格要求的更早被压缩；对一个用来守住硬上限的阈值而言，这是安全的方向。

代价是 token meter 的数字对 CJK 文本不再像字节长度估计，向用户展示占用的部署会看到比提供方计费略大的数字。JSON 工具 schema 保持自己的密度，仍然低估。

恢复路径现在会记录它为什么保留提供方错误，把静默失败变成宿主日志里可诊断的失败。以平铺响应体作答的提供方与网关会被识别；两种形态都不使用的提供方仍回退到 HTTP 状态码。
